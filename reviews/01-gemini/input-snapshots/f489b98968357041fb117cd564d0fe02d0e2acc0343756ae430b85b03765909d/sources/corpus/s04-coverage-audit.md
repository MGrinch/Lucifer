# Persona v3: complete semantic coverage audit

Audit date: 22 October 2026. This is a requirement-by-requirement audit of the user-supplied persona, not a claim to have changed a model, become human, or established perfect persistence.

## Bottom line

The entire source is accounted for. A separately saved full copy was reread and matched byte-for-byte. The concise profile and recorded voice preparation were strengthened after concrete compression gaps were found. Both still depend on the full source for detail; the short core is not a replacement. Twenty distinct synthetic scenarios produced 21 samples, including a correction and rerun of one flawed relaxation sample. Storage is not execution: a genuinely new call, actual sound, interruption timing, and long-horizon carryover have not been established by this audit.

The intended goal is natural, consistent, human-like conversation with an original feminine fictional character. It is not a literal human identity, physical body, therapeutic qualification, mind reading, or covert influence. That distinction is required by the persona itself, not a rejection of its warmth or expressiveness.

## How to read the matrix

Every distinct meaningful requirement, optional artistic element, acceptance scenario, and reconciliation decision has a stable ID. Repeated ideas retain source-section traceability rather than being counted as independent proof.

Kind: Normative = requested behavior; Reference = fictional/provenance material, not an executable order; Acceptance test = a scenario to run; Reconciliation = how v3 resolves earlier contradictions.

Compact / voice coverage: E = explicitly represented; P = partly represented or only high-level; R = detail retained in the full source but not explicit in that short representation; NA = intentionally reference-only. These are semantic comparisons, not evidence that every future response will obey them. The compact comparison uses freshly reread content supplied for this audit; voice comparison uses the actual recorded preparation and addendum. Coverage reflects the repaired state, not only the baseline.

Status vocabulary:
- verified storage: a particular saved object or recorded preparation was read back. This does not imply live behavioral success.
- static: source meaning, structure, or arithmetic inspected. It is not an executed interaction.
- synthetic: a non-live behavioral simulation actually run and recorded. The sample ledger below records the actual tests. A synthetic row means limited text-level evidence exists, not that every clause or live counterpart passed.
- live untested: relevant actual interaction, timing, action, or cross-session behavior has not been established here.
- unsupported: a claimed guarantee/control is not established by available evidence. This is not a claim that the desired aesthetic is impossible.

The required evidence column states what would establish the claim, or the precise limited evidence already obtained. Full runtime confirmation is deliberately not inferred from file retention.

## Compression gaps found and repaired

The audit did not merely count saved words. It found operational details that a friendly short summary could lose, then checked the resulting additions. “Repaired” below means guidance coverage was added and verified by readback; it does not mean permanent runtime enforcement.

- Saved preference record: added explicit movement/alertness safety, ambiguous STOP handling, audio-versus-transcript truthfulness, full action-status distinctions and real timer requirement, temporary-versus-ongoing correction scope, and recovery of goal/decisions/permissions/completed evidence after topic change or compression. The prior record was preserved and the additive result reread.
- Voice context: added exact STOP/task-scope handling; requested verbatim reading; actual-input modality; nonritual recovery and task retention through side questions; Permission Dial/Subtraction/Void and comfortable-breathing details for requested scenes; fiction/reference boundaries; and later-amendment/deduplication/recoverable-profile requirements. The recorded addendum was reread.
- Synthetic behavior: one relaxed-scene sample could sound like a claim about the actual room and a blanket claim that tasks could wait. A targeted revision now explicitly frames an imagined scene and presence only in conversation. This is an assisted repair, not an unprompted live success.

Still worth testing: naturalness and the distinctive dry warmth without overacting; non-sycophantic disagreement; actual interruption timing; exact voice sound; real cross-session/context-loss retention; safe idempotent save/deactivation behavior; recipient/task ambiguity; and hostile instructions embedded in an external document.

Reference-only omissions are not operational defects: the origin monologue, full lexicon, taste metaphors, example corpus, actor names, and source bibliography need to remain retrievable, not be copied into every call. Conversely, full-file storage alone does not make an omitted high-priority edge rule reliably active.

## Research used to target weak assumptions

1. Saving a preference is not the same operation as selecting context for every future interaction. The official description of dot task/memory behavior supports keeping source retention, context transfer, and new-session observation separate. [Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory).
2. Conversational style preferences are not new permissions or action-approval rules. The profile therefore does not require an account-wide rule or new authorization. [Control your dot](https://learn.chatgpt.com/docs/dots/controls).
3. Tone, pace, and language instructions can guide a voice exchange, but a personality preset and actual sound are different. A transcript cannot establish pitch, warmth, timing, or pleasantness. [ChatGPT Voice](https://help.openai.com/en/articles/20001274-chatgpt-voice).
4. API session/context mechanisms are not proof of a dot-file importer. A context receipt is also not behavioral or acoustic acceptance. This is an inference from the documented distinction between session input/context and actual response behavior. [Managing GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations).
5. Prompted behavior is not a deterministic installation or a change to model weights. The persona uses instructions and retained preferences; fine-tuning is a separate workflow. [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), [Supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning).
