# 05 — Reconcile both critiques and release the candidate

## Integrator duty

You are accountable for the final coherent specification, not for making two models appear to agree. Preserve both original reports. Compare each material finding against owner intent, evidence, actual product capability and the rest of the instruction system.

Resolve Grok findings with explicit dispositions. Revisit Gemini decisions when new evidence warrants it; record the revision without erasing the old decision. A plausible new fact is verified before changing a supported installation route.

## Required final audit

- One adult female character, original expression, warm independent judgment, useful action and ordinary conversational freedom remain intact.
- All requirement IDs have current canonical and evaluation mappings.
- No adapter has silently dropped a critical preference or exceeded the actual composed target field's capacity.
- Exact stale-instruction cleanup remains scoped, reversible and supported.
- Real product limits, account access, local/cloud separation and audio uncertainty remain accurately stated.
- Examples do not become rigid scripts. Safety and consent stay proportionate to the selected activity.
- Tools are selected by observed need. The default route has no unnecessary third-party runtime.
- Every finding is accepted/implemented, rejected with evidence, deferred as nonblocking, or left blocking. No unresolved blocker is reclassified merely to pass the gate.

## Release procedure

1. Apply the final coherent edits to the canonical sources.
2. Run `python3 tools/lucifer.py build` and `python3 tools/lucifer.py check`.
3. Run `python3 -m unittest discover -s tests -v`.
4. Complete the Grok integration receipt with the current output fingerprint and pinned report/findings/source evidence. Confirm the Gemini-output → Grok-input chain.
5. Set `workflow/state.json` to `READY_FOR_INSTALL` only when both review integrations are real and complete.
6. Run `python3 tools/lucifer.py gate`. A failure is a concrete unresolved condition, not a request to weaken the checker.
7. Commit/merge the accepted candidate and records into `main`; verify the resulting remote content and actual commit. Record its receipt without altering the candidate's fingerprinted content after the gate.
8. Hand Codex the immutable accepted commit or exact content fingerprint plus `prompts/codex.md`.

An in-scope two-review process already authorizes routine integration. Ask Misha only about a consequential unresolved preference or a real permission boundary. Do not ask him to reapprove every typo, citation correction or scoped instruction improvement.

No settings are applied by the review stage itself. Continue to [stage 06](06-install.md) when installation is already explicitly authorized in the actual task/session, including a conditional instruction whose two-review prerequisite is now satisfied. Otherwise leave the completed handoff ready for the future installation task; do not request redundant permission when it already exists.

## Required remote release proof

Follow `08-git-review-history.md` stages B–C. Complete `reviews/02-grok/publication.json` from the actual contribution, push and merge; verify both review contributions and accepted bytes on private remote `main`. The current content gate is necessary but does not verify GitHub history. Hand the final installer the observed main commit and current fingerprint.
