# 07 — Verify, repair and close

Read `persona.md` §§16–19 and `evals/README.md`. Use the actual surface/model/settings and record them with each result.

Separate four kinds of proof: repository integrity, saved/read-back settings, fresh-session behavior and heard voice. None substitutes for the next. A direct API evaluation does not prove native ChatGPT inherited the same instructions.

Run the planned text/operational cases, representative long-session/resumed-session trajectories, and applicable voice cases. Keep critical failures separate from subjective character preference. Record unavailable devices and untested conditions without converting them into passes.

Use at most two corrective revisions after the initial installation candidate in the first alignment cycle. Change the smallest relevant component, rebuild and retest affected behavior. Preserve the final-set evaluation's status: once used for optimization, it is no longer untouched; add fresh cases for a new claim.

At closure, populate the actual target coverage and operation receipts in a private run location. Commit only a deliberately sanitized summary if needed. Do not publish full account memory, machine backups, raw voice recordings or secret-bearing logs with the repository.

Report the achieved milestone from `goal.md`, the exact accepted specification fingerprint/commit, verified surfaces, partial/unavailable surfaces, measured limitations and precise next actions. A successful save may be complete while behavioral validation remains open. Do not collapse those states into “done everywhere.”

End at [goal.md](../goal.md), using evidence for each claim.
